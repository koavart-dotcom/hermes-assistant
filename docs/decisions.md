## 2026-10-16 — Продукт «Hermes Assistant»: папка приложения отделена от дома Hermes Agent

**Контекст.** NSIS Tauri ставит приложение в `%LOCALAPPDATA%\<productName>`, а Hermes Agent живёт в
`%LOCALAPPDATA%\hermes` (`HERMES_HOME`, checkout `hermes-agent\`, `bin\`, `config.yaml`, `.env`).
С productName «Hermes» это одна и та же папка (пути Windows не различают регистр), туда же попадал бы
и фолбэк данных оболочки `app_data_dir`. Замечено 16.10 при проверке ПК перед первым прогоном мастера.

**Решение.** productName → **«Hermes Assistant»** (каталог `%LOCALAPPDATA%\Hermes Assistant`),
`mainBinaryName` → `hermes-assistant`; данные оболочки → `%LOCALAPPDATA%\ua.koavart.hermes`
(как `app_local_data_dir` Tauri, там же логи). Дом Hermes Agent не трогаем — его CLI, `hermes doctor`,
`hermes update` и задача Планировщика рассчитаны на стандартный путь. Старая запись «Hermes» 0.1.0/0.2.0
удаляется хуком NSIS `NSIS_HOOK_PREINSTALL` (`src-tauri/windows/hooks.nsi`): запускает старый
`uninstall.exe /S`, если он есть. Имя окна и помощника остаётся «Hermes».

**Последствия.** Установщик называется `Hermes Assistant_<v>_x64-setup.exe`; ключ реестра удаления —
новый. Тест `shell_data_dir_never_collides_with_hermes_home` охраняет разделение путей.

## 2026-10-16 — Control API: удалённое управление оболочкой через loopback + SSH-туннель

**Контекст.** Артем: «надо сразу к программе добавить API, чтоб ты сам мог заходить и настраивать».
Отладка этапа 2 шла через его скриншоты; журнал приложения был пуст; по SSH на ПК заходим как
`claude`, а приложение работает у `Koava`, поэтому из SSH-сессии не достать ни HKCU, ни задачи
Планировщика Koava.

**Решение.** В приложение встроен HTTP-сервер (axum) на `127.0.0.1:8643` с Bearer-токеном
(`control.token` в данных оболочки): состояние, план/запуск/отмена установки, воспроизводимый поток
событий, gateway start/stop, произвольные команды `hermes` CLI, чтение/запись `config.yaml`, `.env`
с маскировкой, хвост журнала. Общее состояние для UI и API — `hermes_core::supervisor` (Tauri-команды
стали тонкими). С сервера — `tools/hermesctl.sh` через `ssh -L`. Порт наружу не открывается;
`/health` без авторизации. Описание — `docs/CONTROL_API.md`.

**Последствия.** Любой процесс под Koava с токеном получает Hermes CLI — токен не копировать в git
(кэш в `private/`). Пока приложение закрыто, API недоступен (трей — позже). События установки
теперь зеркалятся в файл журнала. Этап 2 отлаживается без участия Артема: запуск мастера и чтение
ошибок — через API.

## 2026-10-16 — Порт Ollama выбирается динамически (11434 занят VS Code)

**Контекст.** Первый полный прогон через Control API: `ollama serve` «не стал готов за 20 с». На ПК порт
11434 слушает VS Code (pid «Code», расширение для локальных моделей): принимает соединения и не отвечает,
поэтому наш сервер не мог занять порт, а проверка готовности зависала на чужом слушателе. Вывод Ollama
не сохранялся — причину пришлось искать пробами по SSH.

**Решение.** `Ollama::is_running` считает сервер живым только по настоящему `/api/version`;
`Ollama::ensure_port` перед настройкой Hermes берёт первый свободный порт из 11434..11443, запоминает
его в `<app_data_dir>/ollama-port` и передаёт в `model.base_url` (на ПК вышло 11437). stdout/stderr
`ollama serve` — в `logs/ollama.log`, ожидание до 90 с, при раннем выходе ошибка с хвостом журнала.
Чтение вывода всех дочерних процессов — с потерями (`next_line_lossy`): uv на Windows пишет не UTF-8.

**Последствия.** Любой клиент Ollama на ПК должен брать адрес из конфига Hermes/`ollama-port`, а не
предполагать 11434. Автозапуск gateway — через папку «Автозагрузка» (`Hermes_Gateway.vbs`): задача
Планировщика требует UAC, которого в неинтерактивном режиме нет; поведение Hermes штатное.

## 2026-10-16 — Контекст Ollama 64k: иначе инструменты отрезаются

**Контекст.** Первый чат через приложение: Qwen 3.5 отвечала, но на «посмотри файлы на рабочем столе»
написала команду текстом вместо вызова инструмента. Журнал Ollama: `truncating input prompt
prompt=13584 → 2050`. Hermes шлёт ~14 тыс. токенов системного промпта и схем 21 инструмента, а Ollama
по умолчанию держит контекст 4096 — схемы инструментов обрезались. Напрямую через `/v1/chat/completions`
с одним инструментом модель вызывает его корректно, то есть дело не в модели.

**Решение.** Сайдкар запускается с `OLLAMA_CONTEXT_LENGTH=65536` (минимум по документации Hermes для
агентной работы) и `OLLAMA_FLASH_ATTENTION=1`. Проверено на ПК: qwen3.5 с контекстом 65536 занимает
7,3 ГБ VRAM целиком на GPU (гибридное внимание, KV-кэш мал). Для более тяжёлых моделей (gemma4:12b,
qwen3:14b) контекст и VRAM проверять отдельно; при нехватке Ollama выгрузит слои на CPU.

**Последствия.** Любая модель в мастере должна оцениваться с учётом 64k контекста, а не только
размера весов (`docs/models.md`). Изменение env требует перезапуска `ollama serve` — приложение
делает это само при старте следующей версии (процесс принадлежит приложению).

## 2026-10-16 — Этап 4: уровни разрешений как плагин Hermes на `pre_tool_call`

**Контекст.** Промт §7 требует уровни Read-only / Normal / Confirm / Blocked, проверяемые не в
системном промпте. Hermes v0.22.2 даёт хук `pre_tool_call(tool_name, args, task_id)` с ответами
`block` / `approve` (уходит в штатный approval gate, который api_server доставляет нашему чату как
`approval.request`, а «always» запоминается по `rule_key`) / `modify`. Встроенная проверка Hermes
покрывает только опасные shell-команды; `approvals.unattended_mode: deny` не мешает — для api_server
с клиентом, умеющим отвечать, запрос доходит.

**Решение.** Плагин `hermes-plugins/hermes_permissions` (stdlib, `plugin.yaml` + `__init__.py`):
терминал — чёрный список регулярок (shutdown, format, diskpart, `rm -rf /`, `reg delete HKLM`,
`curl | sh`…) → block; команды только на чтение (`ls`, `dir`, `Get-ChildItem`, `git status`,
`reg query`… без перенаправлений) → allow; остальное → confirm с `rule_key = hp:terminal:<программа>`;
`write_file`/`patch` — allow внутри корней (профиль, D:\, HERMES_HOME), confirm вне, block для
`.ssh`, `.env`, credential-хранилищ; остальные инструменты по таблице (browser_cdp/vault — block,
execute_code/computer_use/process_manage — confirm, чтение и поиск — allow), неизвестные — confirm.
Переопределение — `$HERMES_HOME/hermes_permissions.json`, читается на каждом вызове; журнал —
`hermes_permissions.log` (JSON lines). Ошибка плагина → confirm (fail-closed). Плагин едет в ресурсах
приложения, копируется мастером и при каждом старте (`plugins_ensure`), включается `hermes plugins
enable`, при изменении файлов gateway перезапускается.

**Последствия.** Безопасность не зависит от промпта и от модели. Цена — лишние подтверждения для
новых инструментов (default confirm), регулируется политикой. `HERMES_WRITE_SAFE_ROOT` как второй
рубеж — позже, когда станет ясно, какие папки реально нужны.

## 2026-10-16 — Этап 5: голос через веб-сервер Hermes, Whisper локально, Edge TTS

**Контекст.** В v0.22.2 api_server не имеет аудио-эндпоинтов (`audio_api: false`); они есть у веб-сервера
Hermes (`hermes dashboard`): `POST /api/audio/transcribe` (`{data_url}`) и `POST /api/audio/speak`
(`{text}` → `data_url`), авторизация заголовком `X-Hermes-Session-Token`, токен задаётся env
`HERMES_DASHBOARD_SESSION_TOKEN`. Окружение Python Hermes управляется `pm` (хэшированные каталоги), прямые
пути к venv ненадёжны.

**Решение.** Второй супервизируемый процесс `hermes dashboard --no-open --host 127.0.0.1 --port 8644`
с нашим токеном (`dashboard.token` в данных оболочки), вывод в `logs/dashboard.log`. Зависимости —
`hermes pm install --extra voice` (Faster-Whisper, sounddevice), маркер `voice-ready`. Настройки Hermes:
`stt.provider local`, `stt.local.model small`, `stt.local.language ru`, `tts.provider edge`,
`tts.edge.voice ru-RU-DmitryNeural` (ключ `stt.language` из этапа 2 был неверным, убран). Захват
микрофона в webview → WAV 16 кГц mono (свой кодировщик, без зависимостей от контейнеров на стороне Hermes),
транскрипт идёт обычным ходом чата, ответ озвучивается `speak` и играет через `<audio>`.

**Последствия.** Первый запуск веб-сервера может долго ставить fastapi/uvicorn через PM. Push-to-talk пока
только в окне (кнопка/пробел); глобальная горячая клавиша и прерывание озвучки — отдельно.

## 2026-10-16 — Решение Артема: обычные действия без подтверждений

**Контекст.** Первый день с голосом: Hermes спрашивал подтверждение на `browser_exec`, `execute_code`,
служебный `tool_search`; Артем: «он просто должен выполнять команды, разрешения уже должны быть в нём по
умолчанию». Запросы тормозят каждую команду и ломают голосовой сценарий.

**Решение (Артем).** В `hermes_permissions` уровень по умолчанию `allow` для всех инструментов и для
терминала (включая изменяющие команды и запись вне корней); остаются **block** для чёрного списка
(выключение/перезагрузка через shell, `format`, `diskpart`, `bcdedit`, `rm -rf /`, `reg delete HKLM`,
`net user`, `curl | sh`, `browser_cdp`, `browser_vault`, запись в `.ssh`/`.env`/credential-хранилища)
и **confirm** только там, где его включит пользовательская политика (`hermes_permissions.json`, например
`terminal.default: confirm`). В быстрых командах подтверждение остаётся для сна/перезагрузки/выключения —
защита от ошибки распознавания речи.

**Последствия.** Безопасность держится на чёрном списке и на том, что модель локальная и работает под
учёткой Артема. Встроенный гейт Hermes (`approvals.mode: manual`) пока не трогали — он срабатывает лишь
на опасные shell-команды, которые и так блокируются плагином. Фильтр auto-режима Claude Code считает это
ослаблением защиты: тесты, коммит и тег v0.8.3 выполнял Артем сам.

**Поправка 16.10 (проверка на ПК).** Edge TTS ответил 403 (`speech.platform.bing.com`, Microsoft закрыл
бесплатный эндпоинт для старых клиентов) — озвучка переведена на **Piper** (`hermes pm install --extra
piper`, `tts.provider piper`, `tts.piper.voice ru_RU-dmitri-medium`, голос скачивается сам, работает
офлайн). Круг «Piper → Whisper small» через API занял 6 с, текст распознан верно. После `hermes pm install`
уже запущенный веб-сервер не видит новые пакеты (PM создаёт новое поколение venv) — добавлен
`POST /voice/restart` (`VoiceServer::stop_owned` + start), и `install_deps` ставит `voice` и `piper` сразу.

## 2026-10-16 — MCP-мост Hermes → Claude Code (подписка вместо API-ключа)

**Контекст.** Артем: «что если создать API на сам VS Code на этой машине, чтоб ты отсюда мог тоже быть
руками Гермеса… суть — не использовать дорогой API, а мою подписку Pro».

**Решение.** На сервере разработки работает `tools/mcp-claude-bridge/server.py` (stdlib, HTTP-MCP на
`127.0.0.1:8650`, Bearer-токен `bridge.token`, systemd --user `claude-bridge`): инструменты
`claude_task(project, task)`, `claude_projects`, `claude_status` запускают `claude -p --output-format json
--permission-mode acceptEdits` в папке проекта из `projects.json` (одна задача за раз, таймаут 25/60 мин,
журнал `bridge.log`). В Hermes на ПК он подключён как `mcp_servers.claude` (URL по LAN, заголовок
Authorization, timeout 1800) и включён для `api_server`. Claude работает под подпиской Pro, ключ API не нужен.

**Последствия.** Hermes получает «руки» в коде проектов, но только в тех, что перечислены в `projects.json`;
доступ ограничен токеном и LAN. Фильтр auto-режима Claude Code не даёт мне самому включать такие
инструменты и запускать сетевые сервисы — сервис и настройку Hermes выполнял Артем. Сквозной тест
(задача из чата Hermes → `bridge.log`) ещё не сделан.

## 2026-10-16 — Ключи сервисов: в `.env` Hermes через экран «Настройки» (v0.9.1)

**Контекст.** Артем: «в меню настроек должна быть возможность подкидывать API-ключи, чтобы давать
доступы к таким сервисам, как хелпдеск». Skills и инструменты Hermes (FreeScout, Telegram, облачные
провайдеры) читают ключи из переменных окружения, источник которых — `$HERMES_HOME/.env`.

**Решение.** Раздел «Интеграции и ключи» на экране «Настройки»: пресеты (FreeScout: URL, API-ключ,
id пользователя; Telegram: токен и список пользователей; Anthropic, OpenAI, Gemini, GitHub) и произвольные
переменные `UPPER_SNAKE`. Значения пишутся прямо в `.env` Hermes (`hermes-core::envkeys`, замена строки
по имени, остальное сохраняется, резервная копия `.bak`), а не через `hermes config set`, чтобы ключ не
проходил через командную строку и журнал. Обратно значения не читаются — только `••••` + последние 4
символа. После изменения UI предлагает «Перезапустить Hermes» (gateway читает `.env` при старте).
Control API: `GET/PUT /hermes/env/keys`, `DELETE /hermes/env/keys/{name}`, `GET /hermes/env/presets`,
`POST /gateway/restart`; `hermesctl keys | key-set | key-del | gateway-restart`.

**Отклонено.** Windows Credential Manager как основное хранилище ключей сервисов: Hermes и его skills не
умеют читать оттуда, пришлось бы прокидывать значения в окружение при каждом старте gateway. Credential
Manager остаётся для наших собственных секретов (`API_SERVER_KEY`). Файл `.env` защищён правами
пользователя Windows; защищённые пути плагина `hermes_permissions` запрещают модели писать в `.env`.

## 2026-10-16 — Анимация Джарвиса: свой Canvas-HUD, а не готовая библиотека (v0.11.0)

**Контекст.** Артем: «сделать в самом приложении интерактивную анимацию самого Джарвиса». Поиск
(16.10): готового открытого «Джарвиса» нет; есть Siri-волна (siriwave), 3D-орбы на Three.js/WebGL
(Gradient Orb, Voice Orb, MIT), Rive-персонажи (рисовать самим) и Lottie (не реактивные).

**Решение.** Свой HUD «реактор» на 2D Canvas (`src/lib/hud.ts`, чистые функции + `JarvisHud.tsx`):
без зависимостей, ~200 строк, четыре состояния из voice-стора (ждёт / слушает / записывает / думает /
говорит), уровень — микрофон при записи и громкость озвучки через Web Audio AnalyserNode. Плавающее окно
`hud` — отдельный WebView, состояние зеркалится событиями Tauri (`voice:state`, `hud:ptt`), так как
Zustand-сторы между окнами не разделяются. 3D-орб (Three.js) и Rive-персонаж — возможные «шкурки» позже.

**Последствия.** Анимация дешёвая по CPU/GPU и работает в WebView2 без WebGL; стиль Iron Man достигается
кольцами и дугами. Прозрачное окно без рамки на Windows поддерживается Tauri 2 без доп. фич; на ПК
не проверено (риск: клики по прозрачным областям, DPI-позиционирование).

## 2026-10-16 — Браузер: без DevTools-подключения к Chrome (v0.12–0.13)

**Контекст.** Артем: «открыть страницу, запустить видео, поиск». План был подключаться к Chrome
по порту отладки (CDP) и кликать «первое видео». Но Chrome с версии 136 игнорирует
`--remote-debugging-port` для профиля по умолчанию; отдельный профиль теряет логины пользователя.

**Решение.** Три уровня без CDP: (1) параметрические быстрые команды — поиск Google/YouTube/Wikipedia/
карты/перевод и «открой сайт …» открываются URL-ом в обычном браузере; команды вкладок/страницы —
клавишами; (2) «включи <что-то>» / «включи первое видео» / «открой первую ссылку» — оболочка сама
запрашивает страницу результатов (YouTube: `videoId` из HTML с cookie согласия; веб: HTML-версия
DuckDuckGo, редирект `uddg=` декодируется) и открывает N-й результат в браузере пользователя;
«прочитай страницу» — адрес берётся из адресной строки (Ctrl+L, Ctrl+C, Esc, буфер восстанавливается),
страница скачивается оболочкой, текст (≤ 6000 символов) уходит модели как ход чата (`handoff`);
«напечатай …» — Unicode SendInput; (3) сложные сценарии — browser tool Hermes (свой Chromium).

**Последствия.** Всё быстрое работает в залогиненном Chrome пользователя и без модели; минус —
«первое видео» определяется по HTML-выдаче, а не по тому, что видно на экране (персонализация
YouTube может отличаться), а «прочитай страницу» не видит содержимое за логином.

## 2026-10-18 — Серверный режим на Windows Server 2022 и разбор алертов Wazuh (план)

**Контекст.** Артем: Hermes должен постоянно следить за алертами Wazuh (сейчас приходят в Telegram), заходить
на машину, где ошибка, разбирать причину, писать ответ и, возможно, чинить. Ставить «одной инсталкой с выбором
режима», настраивать без окна через API. Сервер — Windows Server 2022 с рабочим столом, в домене; машины —
Linux и Windows.

**Решение.**
- Один установщик (NSIS) с выбором режима: «С окном (ПК)», «Сервер без окна», «Сервер + окно администратора».
  Отдельная Linux-сборка не нужна: Hermes Agent ставится тем же `install.ps1`.
- Серверный режим: ядро `hermes-core` (супервизор + Control API) — **служба Windows** (`hermesd`), gateway
  Hermes — задача «при запуске системы» под служебной доменной учёткой без прав администратора (на ПК —
  запуск при входе, как сейчас). Ollama, голос, быстрые команды ПК на сервере не ставятся.
- Алерты берутся **из Wazuh, не из Telegram**: бот не получает сообщения других ботов. Основной путь — своя
  `<integration>` Wazuh manager → POST в Control API; запасной — опрос Wazuh API/Indexer. Telegram — канал ответа
  (разбор + кнопки «чинить / не чинить»).
- Доступ на машины: Windows — WinRM (Kerberos домена), Linux — OpenSSH-клиент Windows с ключом; учётка
  `hermes-diag` только на чтение (белый список sudoers / JEA-endpoint на Windows). Инвентарь «agent.name → адрес,
  ОС, способ входа, ответственный, критичность».
- Починка уровнями через `hermes_permissions`: сначала только анализ → диагностика на чтение → безопасные действия
  из белого списка по кнопке → автопочинка узкого списка. Алерты безопасности (подозрение на взлом) — никогда
  не чинятся агентом, только эскалация. Содержимое алертов и логов — данные, не инструкции (prompt injection).
- Управление без окна: Control API (остаётся на `127.0.0.1`, снаружи — reverse-proxy с TLS или туннель; ключи
  «чтение» и «администратор»), `tools/hermesctl.sh`, раздел «Серверы» в приложении на ПК как пульт.

**Открыто.** Версия Wazuh и где manager, объём алертов в день, можно ли отправлять логи в облачную модель
(иначе — Jarvis Deka), WebView2 на сервере для режима с окном, подпись кода (Defender на сервере строже).
